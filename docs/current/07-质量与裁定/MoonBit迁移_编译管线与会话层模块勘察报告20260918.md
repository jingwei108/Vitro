## 0. 一页速览（结论先行）

**四条核心判断：**

1. **头号等价性风险 = JSON 数字序列化格式差异（本次实测实证）**。`vitro_cli export` 的产物 schema（`code` / `f64_constants` / `func_table[*].return_type`）语言中立、**可沿用**；但 MoonBit `@json.stringify()` 与 Rust `serde_json` 在浮点上**不逐字节一致**（实测 `1.0`→`1`、`1e20`→`100000000000000000000`、`-0.0`→`0`）。**迁移期禁止对 `bundle.json` 做逐字节 diff**，必须解析后结构化比对（见 ⑧）。缓解事实：当前提交的 Bytecode Libc 产物 `f64_constants` / `i64_constants` / `string_data` / `globals_init_64` **全为空**（`bytecode_libc_data.json:31370,32984,32986,32988`），产物层面暂不触发该差异。

2. **头号架构机会 = `session_api` 的"三出口薄包装"纪律在单出口形态下升级为协议包本体**。现状 `session_api.rs`（703 行）只覆盖协议语义的约 3/4：**`config.set` 写入侧、`session.create` / `session.destroy`、错误 `kind` 映射三块仍在 `vitro_cli.rs` 里**（`:548-564,606-647`）；而 CLI 其余四个子命令（`compile` / `run` / `unified` / `export`）**全部绕开 `session_api`**（`vitro_cli.rs:82,149,289,420`）——同一语义存在两条实现。把 3/4 补齐成 1 并下沉为 `vitro_protocol` 包，是本模块在 MoonBit 下唯一剩下的价值主张。

3. **本模块在途工作为零 patch、纯"已登记未做"**——但其中 **U0#7（C ABI 契约止血）与"砍 capi"决策直接冲突**：U0#7 的 ①②③（`capabilities_json` 改独立分配 / 另 22 入口补 `catch_unwind` / `vitro_capi.h` 补 19 个缺失声明）三项在砍 capi 后**对象不存在**，却是下游 SharpTutor 的当前阻塞项。**若重写未开工，该项不得默认搁置**（见 ④-I1）。

4. **`native/src/vm/` 目录不存在**——`bytecode_libc_loader` 已在 `vitro_vm` crate 内（`vitro_vm/src/lib.rs:3`）。任何"6 个本地模块"的清单里若仍含 `vm/`，即为**已消解的旧结构**。

**规模事实**：本模块 ≈5,200 行（不含 capi 约 4,150），占 `native/src/` 14,324 行的 36%，但**承载了全部出口协议语义**。`compile_pipeline.rs` 793 行中有 **~340 行是两份管线的互相复制**（`:388-553` vs `:600-792`，`:707` 自注"与 `run_compile_pipeline` 相同"）——路线图 U7#4 已登记（`统一整备路线图.md:207`），且 `run_compile_pipeline` **生产代码零调用**（仅 5 个测试文件引用，见 ③-B14）。

## ⑤ 架构优化建议（MoonBit 形态）

### 5.1 先回答评估报告 §4.1 的问题：双轨组织债在包系统下自然消除多少？

**crate 依赖方向【实测，逐个读 `native/crates/*/Cargo.toml`】**

```
vitro_shared (0 crate 依赖，190 行)
   ↑
vitro_ast (→ shared, 1600)
   ↑                     ↑
vitro_lexer (→ shared)   vitro_cpp_frontend (→ ast, 189)   ← 名叫"前端"，实为数据表
   ↑        ↑                 ↑              ↑
vitro_parser (→ shared,ast,lexer)            │              │
   ↑                                         │              │
vitro_typeck (→ shared,ast,lexer,runtime, cpp_frontend, 8851)
vitro_codegen (→ shared,ast,runtime, cpp_frontend, 6265)
vitro_runtime (→ ast, shared, 2056)
vitro_vm (→ ast, runtime, shared, 8885)
vitro_algorithm_steps (0 crate 依赖，2281；由根 crate 的 session.rs/unified re-export 消费)
```

**四条判读**：

1. **crate 层是单向无环的**——评估报告 §7 阶段 1 的"按现有单向依赖顺序逐 crate 平移（`shared → ast → lexer → parser → typeck → codegen → vm`）"（`:298`）**实测成立**，无需重新设计。
2. **`vitro_cpp_frontend` 不是"前端"**：只依赖 `vitro_ast`，被 `typeck`/`codegen` 共享（`typeck/cpp_class_layout.rs:495-496`、`cpp_container.rs:14-15`、`codegen/lib.rs:307-308`、`cpp/range_for.rs:2`）。它是**内置容器布局数据表 + 方法名映射**。在 MoonBit 里应是一个 `vitro_builtin_layout` **数据包**——**不构成反向依赖**，是 Rust 的 crate 命名误导。
3. **真正的债不是 crate 数，而是"crate + 本地模块"两套组织方式并存**（B17）。本地模块中 `compiler/mod.rs`（12 行）与 `shared/mod.rs`（13 行）**是纯 re-export 垫片**（B18）——存在只为保持路径兼容。MoonBit 的包系统（目录即包、`moon.pkg` 显式声明 import）**没有路径兼容承诺的压力**，垫片自然不需要，此债**天然消除**。
4. **一处真实结构问题**：`Session`（`session.rs:62,69`）反向依赖 `engine` 的两个类型，而 `engine/compile_pipeline.rs:12` 又 `use crate::session::*`（B16）。同一 crate 内可编译，MoonBit 包间**必然报循环依赖**——编译器强制拆解，是收益。

**净结论**：双轨债在 MoonBit 下**消除了"两套组织方式"这一半**（垫片无需存在），剩下的一半（包怎么切）变成一次性设计决策，而非持续维护负担。

## ⑦ MoonBit spike 清单

> 每条：**依赖的语言特性 → 最小验证程序 → 判定标准**。标 ✅ 者为本次现场实测（`moon 0.1.20260915`，Windows）；标 ❌/⚠️ 者为环境受限未能完成，附验证方法。

### spike 1：整数溢出语义 ✅ **本次已实测**

- **依赖特性**：`Int` / `Int64` / `UInt` 算术溢出行为
- **最小程序**：`let a : Int = 2147483647; println(a + 1)`；`: Int64` 版；`let u : UInt = 0; println(u - 1)`
- **实测结果**：`Int` → `-2147483648`（**32 位回绕，不 abort**）；`Int64` → `-9223372036854775808`；`UInt` 0-1 → `4294967295`；`-7 / 2` → `-3`、`-7 % 2` → `-1`（**C 语言向零截断语义一致**）
- **判定标准**：与 Vitro 现有**三路径语义收敛**（【文档】`统一整备路线图.md:176` U5#1：JIT wrapping vs 解释器教学 trap 须择一写进 spec）对齐。**结论：MoonBit 默认回绕 = 与 Rust `wrapping_*` 同构**，JIT 路径 wrapping 语义可直接沿用；解释器侧"教学 trap"必须在应用层显式检测（不能指望语言）
- **【待证】**：C 子集规范要求"有符号溢出 UB 按 Clang 行为"时，MoonBit 的确定性回绕**改变了可观测行为**（Clang `-O2` 下可有符号溢出被优化掉）。验证方法：`int x = INT_MAX; x+1;` 三路径下与 Clang `-O2` 对照，按 U5#1 判据裁决

### spike 2：`String`（UTF-16）vs C 字节流 ✅ **本次部分实测**

- **依赖特性**：`String` 内部 UTF-16；`Bytes` 不可变；`FixedArray[Byte]` 可变
- **实测结果**：`s[0]` 返回 `UInt16` code unit（`"hello"[0].to_int() == 104`，ASCII 域等价）；`b"abc".length() == 3`；`FixedArray[Byte]` 可写（`arr[3] = b'A'` → 65）
- **❌ 待证部分（本模块最危险处）**：非 ASCII 域（中文注释/字符串字面量）的**字节偏移 vs code unit 偏移**是否一致。`session_api::output_delta_on` 的游标是**字节偏移**（`session_api.rs:206-212`，含 `is_char_boundary` 前移），`compile_pipeline.rs:152` 的 `source.lines()` 是行边界——两者若在含中文时错位，等价性验收会静默失败
- **验证方法**：写含 `printf("中文")` 的 C 程序 → 取 `output.delta` 分两次游标（`cursor=0` 与 `cursor=<中文字节中点>`）→ 断言 delta 拼接等于一次性读取；并断言 UTF-16 边界处行为
- **判定标准**：`String` 索引、`StringView` 切片、`Bytes` 视图三者在多字节场景下与 Rust 版**逐字节一致**，否则协议包必须全程 `Bytes`（O7）
- **横向证据**：`shared+ast` 勘察报告实测「非 ASCII 列号偏差 −4 独立复现」——同一坐标口径病的另一发作点

### spike 3：1MB 线性内存载体吞吐（评估报告门 1 的具体化）❌ **待证（超出本模块勘察范围）**

- **依赖特性**：`FixedArray[Byte]` / `Array[Byte]` 的可变性 + wasm-gc 下的表示与装箱
- **最小程序**：`FixedArray[Byte]` 分配 1MB（`1048576`）→ 实现 20 个 opcode 的最小 VM（算术 / load / store / 条件跳转 / call）→ 跑 `native/tests/vm_bench.rs` 那条嵌套计数循环（`i<200, j<200`）
- **判定标准**：评估报告门 1 已定：与 Rust 版同口径对比，**慢 3× 以上即出局**（【文档】评估报告 `:289`）。补充判据：单条 `load`/`store` 的 ns 级成本，用于判断是否需要"分页 + 局部缓存"结构
- **验证方法**：需完整 VM 骨架；**建议在阶段 0 门 1 一并做**——它是唯一能让 JIT 归属（I13）有数据支撑的实验
- **关联背景**：现状 `memory: Vec<u8>`（`vitro_vm/src/core/state.rs:80`）是每 opcode 都访问的热路径；评估报告 §2.4 判为**头号技术悬念**（`:124-141`）

### spike 4：JSON 数字序列化格式 ⚠️ **本次已实测，发现真实风险**

- **依赖特性**：`moonbitlang/core/json` 的 `Json::stringify()`
- **实测对照**：

  | 输入 | MoonBit 输出 | Rust `serde_json` 输出 |
  |---|---|---|
  | `1.0` | `1` | `1.0` |
  | `-0.0` | `0` | `-0.0` |
  | `1e20` | `100000000000000000000` | `1e20` |
  | `0.1` | `0.1` | `0.1` |
  | 整数 / `null` / 嵌套对象 | 一致 | 一致 |

- **判定标准**：**这是等价性验收的头号风险点**。`vitro_cli export` 的 `f64_constants`（`vitro_cli.rs:377`）与 `--builtin-libc` 产物（`precompile_bytecode_libc/main.go:414` 逐字节写出）会因此产生 diff
- **缓解事实【实测】**：当前提交产物 `native/crates/vitro_vm/src/bytecode_libc_data.json` 中 `f64_constants: []`（`:31370`）/ `i64_constants: []`（`:32986`）/ `string_data: []`（`:32988`）/ `globals_init_64: []`（`:32984`）**全为空**，`globals_init_32` 仅 `[[0,1]]`（`:32978`），`globals_size: 4`（`:32985`）→ **Bytecode Libc 产物层面当前不触发该差异**；风险仅在"用户代码 export 含浮点常量"的路径
- **行动**：① 等价性验收**不得对 bundle JSON 做逐字节比对**，必须解析后结构化比对（⑧）；② 或在新版定义**规范化数字输出**，从根上消除格式差异；③ 立即做对照实验：同一份含 `double` 常量的 C 源码，两版各 export 一次，逐字段 diff

### spike 5：stdin 逐行读写 ❌ **本次未能验证（环境受限）**

- **依赖特性**：stdout 逐行写；stdin 逐行读
- **实测结论**：
  - ✅ **stdout 逐行写可用**：`println` 正常输出，`moon run` 退出后内容完整（实测 `{"id":1,"method":"run"}` 精确回显）
  - ⚠️ **脚本模式占用 stdin**：`moon run -` 从 stdin 读脚本源码（实测可用）→ **同一进程无法再用 stdin 读数据**。`vitro_cli serve` 的"stdin 请求 / stdout 响应"形态**在脚本模式下不可实现**
  - ❌ **`@stdio.stdin` 未验证**：`moonbitlang/core/env` 只有 `args`/`current_dir`/`get_env_var`/`get_env_vars`/`now`/`rand`/`set_env_var`/`unset_env_var`（`moon ide doc "@env"` 实测），**无 stdin API**；`@stdio` 来自 `moonbitlang/async`，而 `~/.moon` **只读**（实测写入被拒）→ 依赖无法下载，编译报 `Failed to resolve the module dependency graph / 拒绝访问 (os error 5)`
  - ✅ **`moon new` + `cmd/main` 形态可用**：生成 `moon.mod` + `moon.pkg` + `cmd/main/main.mbt`；`moon.pkg` 语法为 **`pkgtype(kind: "executable")`**（**非** `is-main: true` 的旧 JSON 形态——与评估报告 §6.1 记的 v0.10.4 "移除 `moon.pkg.json`" 变更加深一层，属【实测】新事实）
  - ✅ **参数传递实测**：`@env.args()` 返回 `Array[String]`，`argv[0]` 是 **wasm 产物路径**，`--` 之后与直接位置参数均正确传入
- **验证方法**（解除沙箱或换机器后）：`moon add moonbitlang/async` → `cmd/main` 包内 import `moonbitlang/async/stdio` → `for line in @stdio.stdin.lines() { ... }` → 管道喂 3 行 → 断言逐行读回 + EOF 行为
- **判定标准**：① 能逐行读 stdin 且**不吞换行**（⑥-4 的等价要求）；② 能流式写 stdout 且 `flush` 可控（NDJSON 要求每帧即时可见，现状 Rust 显式 `out.flush()`，`vitro_cli.rs:827`）；③ **绑定到 wasm 单文件产物后仍成立**（脚本模式结论不能外推）
- **降级方案（若 stdin 不可用）**：`serve` 改为**预编译 wasm + Node/浏览器宿主**，请求走宿主 bridge 而非进程 stdin——与评估报告 §2.3 的"Node 22+ 作为 CI 主力"宿主判断一致

### spike 6：子进程退出码 ⚠️ **本次部分实测**

- **依赖特性**：进程退出码
- **实测结果**：

  | 情形 | 退出码 | 输出 |
  |---|---:|---|
  | 正常结束 | **0** | — |
  | `abort("boom")` | **1** | `RuntimeError: unreachable at @moonbitlang/core/abort.abort` |
  | 未捕获 `raise` | **1** | 同样落到 `abort` |
  | `@env.exit(3)` | 不存在 | `Value exit not found in package env` |

  - `@sys.exit(Int)` 存在于 `moonbitlang/x/sys`（`moon ide doc` 实测），但**依赖下载受阻未能验证**（同 spike 5）
- **判定标准**：`vitro_cli compile bad.c` 必须以非零退出码结束（⑥-16 的红→绿锚）。**关键问题**：实测可得退出码空间是 `0 / 1`，**无法表达区分度**（现状 Rust 版有"编译失败 exit 1 / 产物缺失 exit 2 / 运行错误 exit 1"）。若 `@sys.exit(n)` 在 wasm-gc 下不可用，则 CLI 只能靠 **stdout/stderr 的结构化输出**供驱动判定——这会改变 `serve_smoke` 的 `exit==0` 断言（`main.go:205,647`）的依赖形态
- **验证方法**：解除沙箱后 `import { "moonbitlang/x/sys" }` → `@sys.exit(3)` → 查 `$LASTEXITCODE`；对 `--target wasm-gc` 与 `--target native` 各测一次
- **行动**：**这项决定 ⑧ 的驱动设计**——若退出码不可用，等价性验收驱动必须改为"解析 stdout 结构化帧 + 超时判死"，而非"查退出码"（评估报告 A2 的 Wasmtime 门 2 亦与此相关）

### spike 7：不可变结构替代 `Arc` 零拷贝共享（评估报告假设 A5）❌ **待证**

- **依赖特性**：MoonBit 不可变值共享语义
- **最小程序**：定义 `struct OutputLog { chunks : Array[(OutputKind, String)] }` → 构造 1 万条 chunk 实例 → 创建"快照"（`let snap = log`）→ 改 `log`（不可变派生新值）→ 测：① 快照是否零拷贝（内存增量）；② `snap` 是否仍读旧内容（COW 正确性）
- **判定标准**：`Arc` 三处（`output` / `trace` / `heatmap`，评估报告 §2.1）替换后，**快照 20 次的宿主 RSS 峰值不超过 Rust 版**（U2#6 归档数据，I3）
- **验证方法**：`moon run --profile --target native --release` 跑循环构造 + 快照；或用进程 RSS 采样（`scripts/internal/probeutil` 同口径）
- **风险**：若 MoonBit 不可变 `Array` 语义是"每次派生全量复制"，`OutputLog` 必须重构为**分块 + 共享前缀**结构，否则每次快照都复制全部输出（评估报告 §2.1 已预判此前提条件）

### spike 8：大体积 JSON 嵌入（563,980 字节产物）❌ **待证**

- **依赖特性**：MoonBit 编译期资源嵌入能力

### spike 9：协议层 checked error 替代 `catch_unwind` ⚠️ **本次部分实测**

- **依赖特性**：`suberror` + `raise` + `try/catch` 的传播与恢复能力
- **实测结果**：`raise` 未捕获 → `RuntimeError: unreachable` + **exit 1**（**不是"可被上层捕获的异常传播"**）；`fn main raise` 可用；`@json.parse` 需 `fn main raise` 才能调用（否则报 `Function with error is not allowed in fn main`，错误码 4122）
- **判定标准**：`serve_handle` 单请求失败必须**不终止进程**（⑥-11 的等价要求）。需验证：`try { serve_handle(...) } catch { err => 返回错误帧 }` 能否捕获**所有**失败路径（含数组越界、整数除零、`abort()`）
- **❌ 未验证的核心问题**：MoonBit 的 `abort()`（panic 等价物）**能否被 `try/catch` 捕获**。若不能，则 serve 的"一条畸形请求不杀会话"护栏在 MoonBit 下**没有对应机制**，必须靠"绝不 abort"的编程纪律 + 参数域前置校验
- **验证方法**：`try { abort("x") } catch { _ => println("caught") }`；以及越界索引 `arr[999]`、`1/0` 三条各测一次
- **判定标准**：三条全部可捕获 → serve 护栏可照搬；任一不可捕获 → 协议层必须做全路径防御（参数域校验 + 无 panic 实现），并把该约束写成不可协商的设计前提

### 8.3 L2 的 `bundle.json` schema 可沿用性裁定

**结论：传输层可沿用；字面层有三处语义非中立、两处形态差异必须先处理。**

**产物清单【实测】**

| 项 | 路径 | 大小 | 性质 |
|---|---|---|---|
| 产物 1 | `native/crates/vitro_vm/src/bytecode_libc_data.json` | **563,980 字节 / 32,989 行 / CRLF** | JSON，`include_str!` 编译期嵌入 |
| 产物 2 | `native/crates/vitro_runtime/src/bytecode_libc_index.rs` | 7,438 字节 / 205 行 / CRLF | 生成的 Rust 常量（**不含指令**，只有索引常量 + 名→索引 match） |
| `bundle.json` | **仓库中不存在** | — | 只是 `AGENTS.md:453` / `AGENTS_EN.md:363` 的示例文件名 |

**顶层 12 字段**（实测）：`code, code_len, f64_constants, func_index, func_table, globals_init_32, globals_init_64, globals_size, i64_constants, source_digest, string_data, version`。实测值：`version=1`、`code_len=3485`、`code` 3485 条、`func_index` 88 条（**1000..1087**）、`func_table` 88 条、`globals_init_32=[[0,1]]`、`globals_size=4`、`source_digest=sha256:1fdb34bf…b2ab`；`code` 中 **37 种 op**、`file_id` 全 0、`loc.line` 最大 536、`Call` 9 条 / `CallHost` 18 条 / `CallPtr` 0 条。

**可沿用的证据**：

- `Instruction` JSON 形态：**`{op, operand, loc}`**——字段名是 **`loc` 不是 `source_loc`**（`vitro_runtime/src/instruction.rs:5-10`）
- `op` 是 **`OpCode` 变体的字符串名**（serde 默认外部标签，实测 37 种）→ **MoonBit 不必复刻 `repr(u8)` 数值即可解析**
- `loc` = `SourceLoc { line, column, file_id }`，`file_id` 带 `serde(default)`（`vitro_shared/src/source_loc.rs:1-9`）
- 加载契约面小而自洽：`version == 1`（`bytecode_libc_loader.rs:63` 有测试断言）、88 个函数固定索引区间与 `bytecode_libc_index.rs:7-10` 的 `CODE_LEN=3485 / BASE_INDEX=1000 / GLOBALS_RESERVED=1024 / FUNC_COUNT=88` 一致

**三处语义非中立（必须处理）**：

1. **`func_table[*].return_type` 是 `vitro_ast::Type` 外部标签枚举**，其 `Array` 变体带 `vla_dims: Vec<Box<Expr>>`（`vitro_ast/src/types.rs:58-65`）、`Typeof` 变体带 `expr: Box<Expr>`（`:98-103`），而 `Expr` 是完整 C/C++ AST 且可序列化（`expr.rs:71-72`）→ **schema 允许把一段源码 AST 嵌进产物**。当前产物实测只出现 **6 种简单形态**（`Void{is_const}` / `Int{is_const,is_unsigned}` / `Char` / `Float` / `Pointer{pointee=Void|Char}`），但这是**"当前数据的性质"不是"schema 的保证"**。**行动**：MoonBit 版 `Type` 序列化形态须逐字段对齐这 6 种，并对 `Array`/`Typeof` 做**显式"不支持即报错"**（fail loud）。**【待证】**：重生成产物是否会出现复杂形态——验证方法为对重生成产物的 `return_type` 去重统计
2. **opcode 的语义**（operand 含义、栈效应）**不在产物里**，只在 `opcode.rs` + 解释器中。实测 `operand` 取值范围 `0..1103515245` → 它是**多项式复用字段**（立即数/地址/索引混用），MoonBit 必须整体移植语义表，**不能按"索引"解释**
3. **`1000+i` 固定索引重定位是 Go 驱动做的**（`precompile_bytecode_libc/main.go:171-217`），Rust `export` 输出的是**原始索引**。MoonBit 若从 `vitro_cli export` 原始产物起步，**必须复刻该映射**（按原始索引升序 → `1000+i`），否则与 `vitro_codegen/src/lib.rs:144` 的预留区间对不上

**两处形态差异（"别逐字节比"的理由）**：

- 仓库提交的产物**键序是字典序**且**多一个 `source_digest`**——因为 Go 驱动把 JSON 解码成 `map[string]any` 后重写（`main.go:163-169` 解码 / `:404-416` 编码，`encoding/json` 对 map 按键排序，注释在 `:398-403`）。**即"export 直接产出的文件"与"仓库提交的产物"字段集与键序都不同**
- `source_digest` **不在 Rust 导出结构体内**（`vitro_cli.rs:303-316`），loader 也无该字段（serde 忽略未知字段）→ 属**构建侧元数据**，不是 VM 输入。算法：`sha256("schema=1\n" ‖ ∀文件: 相对路径 ‖ 0x00 ‖ 内容(CRLF→LF) ‖ 0x00)`（`main.go:88-107`），**CRLF 归一化 + 不依赖 mtime**（`:14-17` 注释说明 CI 干净检出会误报）。MoonBit 版若复刻，**必须同样归一化**（Windows 上是真风险）
- **`--check` 的口径边界【亲读】**：不重新生成、不做逐字节比较、**不校验 `.rs` 与 JSON 的一致性**（只校验两文件存在 + JSON 的 `source_digest`）。因此手改 `bytecode_libc_index.rs` 常量不会被拦；只改 codegen（不动 `runtime_libc/` 源文件）也不会让 digest 变化。**【待证】**：临时改动后跑 `--check` 观察是否仍绿

**三条硬约束**（对应 §③ 的组织债）：

**三条关键切分决策**：

1. **P10 独立成 `vitro_opcode`**：现状 `vitro_runtime`（13 文件 2056 行，**无子目录**）混装 opcode 枚举、instruction、内存常量、`RuntimeState`、`MemoryState`、`unified_types`——**5 个不同关注点**。它是"VM 与会话层共同依赖的底座"，切成 2~3 包可消除"改 opcode 就重编会话层"的耦合
2. **P15 `vitro_protocol` 是三出口纪律的真正载体**：现状 `session_api.rs` 试图承担此角色但被 CLI 绕开（①-1.2）。**验收判据**：`vitro_protocol` 的 `.mbti` 是完整的会话 API 面——现状缺 `config.set` 写入侧、`session.create`/`destroy`、方法名→错误 `kind` 映射三块（散在 `vitro_cli.rs:548-564,606-647`）
3. **P13 与 P14 的边界**：现状 `unified/` 的语义标注读 `session.compile.algorithm_matches`（`session.rs:418-431` 的 `AlgorithmContext for Session`），补全快照由 `compile_pipeline.rs:547,786` 每次成功编译后重建——**两包都依赖编译产物**。建议：`CompileState` 归 P11，P13/P14 通过 P11 的只读接口消费，**不反向依赖 P12**

## 附 C · 三条最需先拍板的事

1. **退出码与 stdin 能力（spike 5/6/9）决定整条驱动链的形态**——建议在阶段 0 一并验证，成本约半天，但它决定 ⑧ 的验收驱动是"查退出码"还是"解析结构化帧"，以及 serve 护栏的可行性。
