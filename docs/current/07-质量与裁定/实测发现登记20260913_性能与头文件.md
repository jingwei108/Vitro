## 1. 性能域

### 1.1 环境

| 项 | 值 |
|---|---|
| CPU | AMD Ryzen AI MAX+ 395（Zen5，16 核 / 32 逻辑，标称 2.99 GHz，单核 boost ~5.1 GHz） |
| 内存层级（实测 pointer chasing 随机环） | 1 MB 工作集 **3.73 ns/访问**；8 MB **95.2 ns**；64 MB 151.7 ns；256 MB 162.9 ns |
| 引擎 | `native/target/release`（2026-09-13 构建） |
| 对照 | Clang 22.1.4（`-O2` / `-O0`）、CPython 3.14.4（`sys._jit.is_enabled() == False`，未启用 JIT） |

> **1 MB 的 L2 正好等于 Vitro 的整个地址空间**——本机让 Vitro 的每次访存都命中 L2。
> 这是本机数据偏乐观的主要机制，读绝对值时必须带上这条前提（见 §4.3）。

### 1.2 Vitro 各执行路径的绝对数据（`vitro_cli run`，扣 10.2 ms 启动底价）

VM 步数取自 `serve` 的 `steps_executed`（引擎自报口径）。

| 负载 | 墙钟 min | 执行段 | VM 步数 | ns/VM 步 | 路径 |
|---|---|---|---|---|---|
| 500k 次 `s += i` | 42.2 ms | 32.0 ms | 9,000,226 | **3.56** | JIT 生效 |
| 500×500 嵌套内层 | 25.8 ms | 15.6 ms | 4,510,032 | **3.46** | JIT 生效 |
| 200 元素逆序冒泡 | 22.4 ms | 12.2 ms | 1,805,640 | **6.76** | JIT 生效 |
| `fib(24)` 递归 | 82.0 ms | 71.8 ms | 2,025,670 | **35.4** | 纯解释 |
| 300k 次函数调用循环 | 306.1 ms | 295.9 ms | 7,200,027 | **41.1** | 纯解释 |
| 20k 次 `malloc`+`free` | 903.5 ms | 893.3 ms | — | 44.65 **μs/次** | 纯解释 + 超线性 |

**JIT 加速比**（`cargo test --release --test vm_bench -- --nocapture`，JIT 开 / 真禁用开关对照）：

| 用例 | JIT | 纯解释 | 加速比 |
|---|---|---|---|
| `nested_loop_1k` | 0.1018 s | 0.8953 s | **8.80×** |
| `array_sum_200k` | 0.0206 s | 0.1631 s | **7.92×** |
| `factorial_recursive_10` | 0.0011 s | 0.0012 s | 1.11×（噪声，递归无回边 → JIT 不适用） |

**统一模式（时间旅行）**：18,226 步 / 1.067 s ≈ **58.5 μs/步**（比 `run` 路径慢 ~700~1500×）。
与 2026-06-19 基线（52.3 μs/步、19,107 步/秒）同量级，属既有成本，非回归。

**编译速度**（含进程启动）：Vitro `compile` **6.3~6.8 ms** vs `clang -O2` **150~160 ms** ≈ 快 **22×**。

### 1.3 三方对比（每单位工作量）

| 单位 | Vitro | CPython 3.14 | clang -O2 | Vitro÷CPython | Vitro÷native |
|---|---|---|---|---|---|
| 循环累加 1 次迭代 | 64 ns | 42.2 ns | 折叠，不可比 | **1.5×** | — |
| 嵌套内层 1 次迭代 | 62 ns | 28.4 ns | 折叠，不可比 | **2.2×** | — |
| 冒泡 1 次比较 | 613 ns | 136 ns | 3.3 ns | **4.5×** | **186×** |
| fib 1 次递归调用 | 478 ns | 23.9 ns | 折叠，不可比 | **20×** | — |
| `malloc`+`free` 1 次 | 44,650 ns | — | 1.68 ns（-O2）/ 24.5 ns（-O0） | — | **26,600× / 1,820×** |

> **native 侧的可比性警告**：`clang -O2` 把累加循环换成闭式求和、把 `fib(34)` 编译期求值，
> 所以累加/嵌套/fib 三行的 native 数字**无效**，本文不用于结论；只有**冒泡比较**与
> **malloc/free** 两个不可优化负载可比。

### 1.4 分解：为什么是这个倍率

| 引擎 | 每基本操作成本 | 一条 `s += i` 的操作数 | 每迭代 |
|---|---|---|---|
| Vitro 纯解释 | **35~41 ns / VM 步** | **18 步** | ~666 ns（推算） |
| Vitro JIT | **3.5 ns / VM 步** | 18 步 | 64 ns |
| CPython 3.14 | **~6 ns / 字节码**（42.2 ns ÷ 7 条，`dis` 实测 `FOR_ITER/STORE/LOAD×2/BINARY_OP/STORE/JUMP_BACKWARD`） | **7 条** | 42 ns |
| clang -O2 native | ~0.3 ns / 指令 | ~5 条 | 0.6~17 ns |

**结论**：Vitro 在解释路径上同时承受"单步成本 5~6×"与"步数膨胀 ~2.5×"，两者相乘即
比 CPython 慢 15~20×；JIT 把最内层热循环拉回 3.5 ns/步，才反超到只慢 1.5×。

### 1.5 P-1：`malloc`/`free` 超线性（最严重的性能缺陷）

- **实测**：2 万次 `malloc(16)`+`free` = 893 ms（44.65 μs/次）；规模 ×5（10 万次）时工程
  记录为 8.94 s（`重构评估报告20260912.md`）——**规模 ×5 → 时间 ×10**，确认超线性（O(N²)）。
- **根因（代码级，仍在线）**：`freed_logs` / `regions` 为 `Vec` 线性扫描——
  `native/crates/vitro_vm/src/core/state.rs:607`（`freed_logs.iter().any(...)`）、
  `native/crates/vitro_vm/src/host/memory.rs:73,127`（`.iter().find(...)`）。
- **处置方向（既有）**：`统一整备路线图.md` Phase 2「regions 登记表重构 + O(1)/O(log N) 索引」
  已列，未落地。这是单点收益最大的性能项。

### 1.6 处置建议（按投入产出排序）

1. **P-1 索引化**（O(N²) → O(log N)）：收益最大，且是缺陷而非取舍。
2. **P-2 dispatch/指令融合**：35 ns → 10 ns 级，全局收益。
3. **P-3 降低步数膨胀**：codegen 逐 AST 节点直译是根因，改动面大、风险高。
4. **P-4 扩大 JIT 覆盖面**：涉语义正确性（2026-09-13 的静默错值即出在此），须配 J10 式防线。

## 2. 头文件域

### 2.1 机制概要（先说清不是缺陷的部分）

| 部件 | 实现 | 位置 |
|---|---|---|
| 标准库存根 | **14 个名字的硬编码白名单**，`include_str!` 编译期嵌入 `runtime_libc/include/*.h` | `native/crates/vitro_lexer/src/preprocessor/resolver.rs:144-162` |
| 自定义头文件 | 文件系统读取，候选链 = 当前文件目录（`dir_stack` 顶）→ 源文件目录 | `resolver.rs:39-51` |
| include-once | `processed: HashSet<规范路径>`，守卫语义内置 | `resolver.rs:20,69-85` |
| 环检测 | 静态 DFS（深度 ≤16 / 节点 ≤64）→ `E1015` fail-soft 跳过 | `resolver.rs:98-141` |
| 包含者目录优先 | 往头文件内容首尾注入 `#__vitro_push_dir` / `#__vitro_pop_dir` **哨兵指令** | `directives.rs:342-356` |

设计定位见 `结构重构与C23锚定决议.md` §3：**include 内核抄的是 Zig `@import` / C++20 modules
的 ModuleGraph 语义（once + 依赖图 + 环检测），表面保留 C 的文本包含语法**。这不是"不吃头文件"。

### 2.2 能力矩阵（15 个探针，Vitro vs Clang 22.1.4）

| T3 | 上级 `"../up/h.h"` | ✅ 333 | ✅ | 一致 |

### 2.3 H-1：找不到头文件 → 静默跳过、零诊断（P0）

- **代码位置**：`native/crates/vitro_lexer/src/preprocessor/directives.rs:340`

  ```rust
  let Some(mut content) = content else { return };   // ← 无任何诊断
  ```

- **实测表现**：`#include "no_such_header.h"` 不产生任何错误；错误延后到使用点，
  报 `3:32 未声明的变量 'NO_SUCH_MACRO' (E3023)`——**真正的问题在第 2 行的 include**。
- **影响**：与项目"错误可教学（中文诊断 + 修复建议 + 错误码）"的核心定位**直接冲突**；
  学生按提示去找变量声明，永远找不到根因。
- **Clang 对照**：`fatal error: 'no_such_header.h' file not found`（位置精确到 include 行）。
- **处置建议**：新增 `E1014_IncludeNotFound`（或复用既有码），在 include 所在行报错并列出
  已搜索的目录（当前文件目录 / 源文件目录）。

### 2.4 H-2：`__has_include` 与 `#include` 口径不一致（P0，新发现）

- **代码级根因**：
  - `has_include()`（`resolver.rs:88-93`）**只用 `base_path`**（源文件目录）；
  - `resolve_path()`（`resolver.rs:39-51`）**优先 `current_dir()`**（`dir_stack` 顶 = 包含者目录）。
  - 于是在**头文件内部**（`dir_stack` 非空）两者判定不一致。
- **实测**（T14）：`nest/outer.h` 内 `__has_include("inner.h")` 判定为 **0**，
  而紧随其后的 `#include "inner.h"` **成功**；Clang 两者均为 1。
- **影响**：用 `__has_include` 做特性探测的头文件在 Vitro 里会**静默走 `#else` 分支**，
  而能力实际存在（条件编译分支选错，且无诊断）。这是**未登记的 Clang 差异**，
  按"Golden 只能来自 Clang"的纪律应立刻入 `*_FAILURES.md`。
- **处置建议**：抽出统一候选链（`current_dir()` 优先 → `base_path`），`has_include` 与
  `resolve_path` 共用；修复后把 T14 固化为 shadow 回归用例（**先红后绿**）。

### 2.5 H-3 / H-4 / H-5

- **H-3（`<>` 语义放宽）**：`<>` 也查源文件目录（T4 实测加载成功，Clang 拒绝）。
  方向上是"更容易通过"，但会制造"Vitro 能编、Clang 编不过"的假象，**破坏 shadow 前提**。
  建议：`<>` 只查存根表，`""` 才走文件系统候选链。
- **H-4（存根硬遮蔽）**：`load_stub()` 按**名字**判定且顺序先于文件系统（T7 实测），
  用户无法提供自己的 `stdio.h`。教学影响小，但意味着存根不可替换/扩展。
- **H-5（wasm 下自定义 include 静默失效）**：`resolve_path` 之后走
  `std::fs::read_to_string(...).ok()`——wasm32-unknown-unknown 无文件系统且 `.ok()` 吞错，
  所以 wasm 下**只有存根可用**，自定义 include 是静默降级。属跨平台缺口，
  与 §3 的 CI 单平台问题同源。

## 3. 跨平台相关（本轮顺带确认，登记备查）

| 项 | 实测 | 影响 |
|---|---|---|
| CI 平台覆盖 | `.github/workflows/ci.yml` **只有一个 job，`runs-on: windows-latest`** | Linux/macOS 从未验证；Go 驱动已踩过 `pathlib` 排序平台差异（Windows casefold 序 vs Linux 码点序） |
| wasm 出口 | `cargo build --target wasm32-unknown-unknown --release` 20.7 s 通过，`vitro_native.wasm` 3.44 MB；`scripts/wasm_smoke/wasm_smoke.js` **11/11 PASS** | 出口活性确认；但见 H-5 与"wasm 无运行时行为实测"（裁定 J4 红） |

## 4. 测量口径与已知偏差（P-6）

> 本节是**方法学告警**：本文所有绝对值只在下列条件下成立，跨条件引用会失真。

### 4.1 后台负载会显著污染基准（实测踩坑）

首轮测量时后台正在跑 `cargo test --release`（编译），Vitro 侧数字全面偏慢：

| 指标 | 受污染 | 干净重测 |
|---|---|---|
| hello 底价 | 36 ms | **10.2 ms** |
| 500k 热循环 | 132 ms | **42.2 ms** |
| 纯解释吞吐 | ~11 M 步/s | **~24 M 步/s** |

**教训**：基准必须在空载下测；同机多任务时 Vitro 侧可偏慢 2~3×。

### 4.2 "空载单线程"不是稳定条件

| 条件 | 实测影响 |
|---|---|
| 不绑核 vs 绑单核（同一负载） | 45.2 ms → 61~65 ms（**+40%**，进程加载阶段被串行化） |
| 不同逻辑核之间 | ±6% |
| 与 1 个忙进程共享同一逻辑核 | Vitro **2.13~2.49×** / native 1.93× / CPython 1.61×（后者被 47 ms 启动稀释） |
| 15 个物理核满载（测量核独占） | Vitro **1.99×** |
| 31 个逻辑核全饱和 | Vitro **2.65×**（含 SMT 兄弟竞争） |
| 对照实验（忙进程绑到别的核） | 1.00× ✅ 实验设计有效 |

### 4.3 外推边界

- **绝对值不可外推**：本机为高端 CPU（大 L2、5.1 GHz boost、高带宽），且 Vitro 的 1 MB
  地址空间 100% 命中 L2。低端设备上解释路径 **［推断］** 再慢 2~4×。
- **倍率相对稳健**：三方同机同条件测量，硬件红利大体等比抵消（§4.2 的算力减半实验直接
  支持这一点：Vitro 2.13× vs native 1.93×，量级一致）。
- **结构性结论与机器无关**：H-1/H-2 的语义缺陷、P-1 的超线性、P-3 的步数膨胀，
  换任何机器都成立；**［推断］** 在弱机上 Vitro 相对 native 的差距更可能**扩大**
  （解释器的间接分支预测与访存对低端微架构更敏感），而非缩小。
