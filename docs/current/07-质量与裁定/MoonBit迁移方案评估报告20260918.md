## 0. 一句话结论

**提案的三条基础事实里有一条是错的（风险定位错位），另有一条未经验证；而真正的头号风险方案里没有出现。**

具体地：提案把"GC 语言做时间旅行 = 深克隆对象图"当作唯一技术悬念——实测该风险**不存在**，
因为现版快照早已是扁平值结构。提案完全未覆盖的头号风险是 **VM 热循环在 wasm-gc 下的性能**
（1MB 内存的承载类型直接决定每指令的开销）。

单出口形态本身是**成立且有真实收益**的（砍 capi 消掉一类长期义务），
但收益兑现的前提是三个假设全部成立——本节第 7 章给出可在 1~2 周内证伪的方案。

## 1. 提案主张摘要

为免歪曲，先如实复述提案的五个主张：

| # | 主张 |
|---|------|
| P1 | WasmGC 已是正式标准，四大引擎默认支持，长尾缺口降级为"最低浏览器版本声明" |
| P2 | wasm-gc 单出口、多宿主：浏览器（主交付）/ Node 22+（CI 主力）/ 服务端 wasm 运行时（OJ 批量） |
| P3 | 开发期另有本地通道：MoonBit 的 C 后端（`MOONBIT_NEW_NATIVE=0`）出本地可执行文件用于单步调试 |
| P4 | **唯一真正的技术悬念**：快照要求状态可克隆，MoonBit 是 GC 语言 → 深克隆对象图，又慢又易漏字段；解法是"状态扁平化铁律" |
| P5 | 下游动荡、一年内不接入 → 现在是破坏性重构窗口 |

**P1、P5 经核查成立。P2 部分成立（见 §2.3）。P3 表述有误（见 §2.2）。P4 命题不成立（见 §2.1）。**

## 2. 事实核查：四处需要修正的判断

### 2.1 P4 命题不成立——快照早已是扁平的，不存在"深克隆对象图"

**代码证据**（`native/crates/vitro_vm/src/snapshot.rs`）：

```rust
pub enum MemoryImage {
    Full(Vec<u8>),                                        // 完整 1MB 字节数组
    Delta { base_step: i32, pages: Vec<(u16, Vec<u8>)> },  // 4KB 脏页增量
}

pub struct VMSnapshot {
    pub memory: MemoryImage,          // 字节拷贝，O(n) 早已达成
    pub stack: Vec<u64>,              // 扁平
    pub call_stack: Vec<CallFrame>,   // 字段全为标量
    pub snapshot_vars: HashMap<String, u64>,
    pub freed_logs: BTreeMap<u32, FreedRegionInfo>,
    // ... 其余均为标量或 Vec
}

pub struct MemorySnapshot {
    pub regions: Vec<MemoryRegionData>,
    pub free_list: Vec<FreeBlock>,
    pub quarantine: std::collections::VecDeque<FreeBlock>,
    pub quarantine_bytes: i32,
    pub quarantine_budget: i32,
    pub heap_base: u32,
    pub heap_offset: u32,
    pub alloc_counter: i32,
}
```

`CheckpointManager` 另有 `PAGE_SIZE = 4096`、`PAGE_COUNT = 256`、`max_checkpoints = 50`、
`full_every = 5`、`smart_mode` 控制流边界加检——**"把状态放进扁平数组、快照退化为字节拷贝"
这件事是现存的实现，不是待建设计**。提案描述的"又慢又易漏字段"不描述本仓库。

**结论**：P4 应从"结构性技术悬念"降级为"照抄现有设计"，风险等级下调。

**但提案漏了两个 Rust 特有机制**，它们在移植时才是真问题：

1. **`Arc` 零拷贝共享**。`RuntimeSnapshot` 中仅有的三处共享指针：
   `output: Arc<OutputLog>`、`trace: Arc<Vec<TraceEntryData>>`、`heatmap: Arc<ExecutionHeatmap>`
   （`native/crates/vitro_runtime/src/runtime_state.rs`）。
   Rust 用引用计数达成"快照克隆大对象不复制"。MoonBit 无 Arc；
   替代路径是"不可变结构天然可共享"——**该替代成立且更简洁**（不必手写 Arc），
   但前置条件是这三个结构真的做成不可变，否则每次快照仍会复制输出与轨迹。
2. **`CallFrame` 内嵌 `String` 与嵌套 `Vec`**（`native/crates/vitro_vm/src/core/state.rs:35`）：
   `func_name: String` + `local_buffers: Vec<LocalBuffer>`，随快照逐帧克隆。
   MoonBit 的 `String` 不可变 → 共享免费，**这一项迁移后反而变好**。

### 2.2 P3 表述有误——`MOONBIT_NEW_NATIVE=0` 不是"启用本地可执行文件"

依据 MoonBit v0.10.4 官方发布说明（2026-07-13）：

| 事实 | 内容 |
|------|------|
| 该变量的真实语义 | **禁用新原生后端**，使 debug 与 release **都走 C 后端** |
| 平台默认 | 新原生后端仅在 macOS Apple Silicon 默认启用；**其他平台默认即 C 后端** |
| Windows 现状 | 本次评估环境为 Windows——默认本就走 C 后端，该变量基本无需设置 |
| release 原生构建 | 走 C 后端并**调用系统 C 编译器 `-O2`** |

**衍生成本（提案未计）**：MoonBit 的 release 原生构建会引入 **C 工具链依赖**。
本仓库当前是"3 个非 wasm 运行时依赖、零 C 依赖"（见
`reports/项目规模与难度评估_2026-09-14.md` §4.2，依赖复杂度 ★1，为全项目负担最轻的维度）。
换语言会把这一项从 ★1 拉高。
**注**：MoonBit 另有 LLVM 后端与 LLVM Debugger（2025 年发布，支持 LLDB / VSCode CodeLLDB
源码级调试），调试体验优于 C 后端路径，提案可改走此路。

### 2.3 P2 的第三宿主未经验证——"服务端 wasm 运行时复用同一产物"缺证

| 宿主 | 证据状态 |
|------|----------|
| 浏览器 | ✅ 有实证（WasmGC 四引擎默认支持，提案查证准确） |
| Node 22+ | ✅ 有实证——`pptx-svg`（约 3 万行 MoonBit + 3,600 行 TS，两个月完成）编译至 wasm-gc，**产物无外部运行时依赖，可在浏览器与 Node.js 运行**，Wasm 体积约 280KB |
| 服务端 wasm 运行时（Wasmtime 类） | ❌ **无任何证据支持**；且有反证倾向 |

反证倾向来自两处：DeepWiki 明示 "MoonBit programs compiled to WASM or JS
**rely on a glue layer** to interface with the host environment"；官方 `moonbitlang/async`
的 `.wasm` 产物"**必须用最新 moonrun 运行，尚不兼容其他 Wasm 运行时**"。
MoonBit 的 wasm-gc 产物是否只依赖标准 WasmGC 指令与标准 JS glue、能否直接进 Wasmtime，
**必须先 POC**（见 §7 门 2）。这条现在是"待证"，不能写进方案当既成事实。

### 2.4 头号技术悬念方案里没有出现——VM 热循环性能

**代码证据**：`native/crates/vitro_vm/src/core/state.rs:80`

```rust
pub(crate) memory: Vec<u8>,   // 1MB 线性内存 = 堆上连续字节数组
```

这是**每个 opcode 都要访问**的热路径。在 MoonBit / wasm-gc 下：

- MoonBit 的 `Bytes` 是**不可变**的，无法承载"每步都写"的程序内存；
- 因此必须改用 `FixedArray[Byte]` / `Array[Byte]` 一类可变载体；
- **这些载体在 wasm-gc 下是否为 packed 表示、每次索引读写是否需要解装箱/边界检查，
  直接决定 VM 吞吐**。

**为什么这条比 P4 重要**：快照是每 N 步一次的偶发操作（`interval` 控制、`max_checkpoints = 50` 上限）；
内存访问是每条指令一次。若此处性能不达标，已被实测锚定的性能资产会全部作废——
包括 JIT 的 9.16×（嵌套循环）/ 9.4~9.7×（单层）与 UAF 扫描的 1.45s。

## 3. 提案未覆盖的三项决策

### 3.1 JIT（Phase 25）的归宿

JIT（trace-based loop accelerator）是本项目少有的**实测性能资产**，
且经《核心资产重构裁定》专门裁定过（详见 `docs/current/07-质量与裁定/核心资产重构裁定.md` §14）。
方案全文未提及。wasm-gc 下需裁三选一：

| 选项 | 说明 |
|------|------|
| 保留 | MoonBit 无函数指针，但有闭包 / FuncRef，理论可重做 trace 序列；工作量接近重写 |
| 重写 | 同上，且需重立 `jit_path_parity` 那条八条三锚差分防线 |
| 放弃 | **需论证**：原 JIT 的动机是移动端慢 CPU + 禁运行时代码生成；宿主换为浏览器 V8（自带 wasm JIT）后，自研 trace JIT 的边际收益可能大幅缩水 |

**建议**：在阶段 0 一并实测"MoonBit wasm-gc 原生执行"与"Rust + JIT"的同口径吞吐，
用数据决定第 3 项是否成立，而不是默认"跟着搬"。

### 3.2 C++ 子集（Phase 31–41）的归宿

C++ 扩展占 **11 个 Phase**，是本项目最难的部分（类 / 继承 / 模板单态化 / 虚函数 /
this / 构造析构 RAII / `new[]`-`delete[]` / 引用 / 移动构造 / `unique_ptr`）。
实测规模（`reports/facts.json`，as_of 2026-09-18）：

| key | 值 | 单位 |
|-----|-----|------|
| `cpp_e2e_cases` | 83 | 用例 |
| `shadow_cpp_cases` | 99 | 用例 |
| `shadow_cpp_match` | 95 | 用例 |
| `cpp_failures_active` | 1 | 条 |

**口径说明（避免误读）**：`CPP_FAILURES.md` 的**历史累计记录**约 40 条
（口径见 `reports/项目规模与难度评估_2026-09-14.md` §5.1），
而**当前 active 未解决为 1 条**（`cpp_failures_active`，as_of 2026-09-14）。
两者不是同一口径。

**决策**：C++ 子集跟着搬到 MoonBit，还是砍掉？这一项决定重写规模的三分之一量级，
必须在阶段 0 之前拍板——不能拖到重写途中发现。

### 3.3 防线的重建期（裸奔期）

提案称"六站双轨对账的方法论原样复用"——**方法论可复用，判对**。但需补充三点：

1. **驱动链必须重建**：`shadow_verify` 走 ctypes 调 `vitro_native.dll`；
   换 wasm-gc + Node 宿主后该通道不存在，需重建整条驱动。
2. **golden 真值可直接复用**（提案判对）：Clang / Clang++ 产出的 `.out` 不因实现语言变化而失效，
   这是重写中**最大的可复用资产**。
3. **重建期存在"裸奔期"**：防线 1~5 在新语言下重建期间检测能力为 0。
   而《项目规模与难度评估_2026-09-14》§5.2 归纳的 A/B/C 三类易错点
   （跨层语义失配 / 启发式判据误判 / 时序与生命周期）**全部是"不报错只错值"**——
   裸奔期即静默错值高发期。

## 5. 提案判断正确的部分

1. **P1 成立**：WasmGC 已成为正式标准，Chrome 119（2023-10 首发）/ Edge（同步）/
   Firefox 120（2023 底）/ Safari 18（2024 收尾）全部默认支持。
   "从结构性风险降级为版本要求声明"的判断准确。
2. **P5 成立**：下游动荡、一年内不接入，确实是破坏性重构的最佳窗口，且不可复制。
3. **golden 真值可复用**（见 §3.3 第 2 点）。
4. **JSON-lines 协议层可复用**：`serve` 的 wire format 已语言中立，提案判断正确。
5. **砍 capi 是真实收益**：单出口消掉 C ABI 的 45 个导出函数与 `vitro_abi_version()`
   版本化承诺（当前 `abi_version` = 2.1.0，as_of 2026-09-14）。这是**消掉一类长期对外义务**，
   而非节省工作量——价值真实。
6. **形态与定位吻合**：第三方评估（asopi.tech，2026-07）明指 MoonBit
   "good fit for **parsers, algorithms, and data processing**"；
   `pptx-svg` 的"Wasm 核心 + TS 做 I/O"分工模式，与本项目
   "引擎留在后端、前端切割给社区"的定位几乎是同一模板。

## 6. 外部环境风险

### 6.1 MoonBit 自身成熟度

| 事实 | 内容 |
|------|------|
| 官方自述阶段 | **beta-preview**（官网原文；同时称"可用于生产环境"） |
| 里程碑 | 2023-08-18 首发；2025-06-18 进入 Beta |
| 1.0 时间 | 官方路线图为 2026 年中旬；网易 2026 年报道称"预计九月发布"——**即本月** |
| 近期 breaking change | v0.10.4（2026-07-13）：**移除 `moon.pkg.json` / `moon.mod.json`**、warnings 配置去 `@` 语法 |
| 长期性 | IDE A 研究院（沈向洋创立；项目技术负责人梅宏院士；首席科学家张宏波，ReScript 作者、前 OCaml 核心开发）；用户数超 10 万；3000+ 社区库；1,000 万行代码 |

**判读**：团队与学术背景强，但相对 Rust（数百万用户、十余年工业验证）
**风险等级不同——这是"押注"而非"选择"**。在语言 1.0 发布当月启动 5.2 万行重写，
意味着未来 2~3 年需跟随其 breaking change。

### 6.2 LLM 生成效率（本项目高度依赖）

IEEE 论文《No Resource, No Benchmarks, No Problem? Evaluating and Improving
LLMs for Code Generation in No-Resource Languages》**将 MoonBit 归类为 no-resource language**，
实测：McEval 困难基准上 Qwen 2.5 Coder 32B Base 的 pass@1 为 **25.86%**
（对照组 Gleam 12.47%；经 instruction transfer 后 32.60% vs 26.08%）。

**影响**：本仓库有专门的《人机协作代码模式审计》，代码高度依赖 AI 生成。
**重写效率会显著低于在 Rust 下的经验**。

**建议**：这既是宣传（官方强调 AI-native）与实证（论文 pass@1 25.86%）冲突之处，
**不应采信任何一方**。阶段 0 增加一项半天的对照实测：
取 20 个 VM / 编译器相关函数为样本，测同一模型的 MoonBit 一次通过率，
与 Rust 基线对比（见 §7 门 0）。

## 7. 建议路线

**不做"做/不做"的二选一。建议先做 1~2 周的阶段 0，任一门红即整份回退。**

### 阶段 0：四道证伪门（1~2 周，不触碰现有仓库）

| 门 | 验证内容 | 判定标准 | 失败后果 |
|----|----------|----------|----------|
| 门 0 | LLM 生成效率对照（20 个样本函数） | 一次通过率与 Rust 基线**同量级** | 重写周期不可估 → 回退 |
| 门 1 | **VM 热循环性能** | MoonBit wasm-gc 最小 VM（1MB `FixedArray[Byte]` + 20 opcode + 栈）跑 `vm_bench` 那条嵌套计数循环，与 Rust 版同口径；**慢 3× 以上即出局** | 单出口收益不划算 → 回退 |
| 门 2 | Wasmtime 可移植性 | MoonBit wasm-gc 产物丢进 Wasmtime 跑通 | 删掉"服务端 wasm 运行时"形态，非致命 |
| 门 3 | 快照往返正确性 | `VMSnapshot` 全字段在 MoonBit 建一遍；seek 回第 5 步；验证 `quarantine` / `quarantine_bytes` / `quarantine_budget` 随快照往返；UAF 检测不出假阴性 | P4 降级结论被推翻 → 回退 |

**门 1 决定生死，门 0 决定周期，门 3 验证本报告 §2.1 的降级结论是否可靠。**

### 阶段 1（全绿后）：golden 先立，再搬内核

1. 先在 MoonBit 侧建立 golden 真值（Clang `.out`）与 JSON-lines 协议层；
2. 按现有单向依赖顺序**逐 crate 平移**：`shared → ast → lexer → parser → typeck → codegen → vm`
   （该顺序是现成的，无需重新设计）；
3. **每搬一个 crate，趁 Rust 版仍在时做差分扫描**——这是唯一"不重踩坑"的路径；
4. 快照与检查点管理器**照抄现版设计**（§2.1），不重新设计。
